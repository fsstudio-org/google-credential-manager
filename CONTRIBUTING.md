# Contributing

Contributions are welcome, large or small. Please read the [code of conduct](./CODE_OF_CONDUCT.md) first — this should be a friendly and respectful place.

**The most valuable contribution right now is an iOS bug report.** The iOS path has never been run on a device; see [platform status](README.md#platform-status).

## Layout

This is a single package, not a monorepo:

- The library itself lives in the root — [src/](src/) (JS facade + TurboModule spec), [android/](android/), [ios/](ios/), [plugin/](plugin/) (Expo config plugin).
- [example/](example/) is a standalone Expo app with its own dependency tree. It is **not** a workspace; you install it separately.

The package manager is **pnpm** (there's a `pnpm-lock.yaml`). Node version is in [.nvmrc](./.nvmrc).

```sh
pnpm install
```

## Checks

These are what CI runs, and they're the whole story for the JS layer:

```sh
pnpm lint        # eslint + prettier
pnpm lint --fix  # fix formatting
pnpm typecheck   # tsc --noEmit
pnpm test        # jest
pnpm build       # react-native-builder-bob -> lib/ (also run by `pnpm install`)
```

`lib/` is what gets published and is gitignored; never edit it by hand.

Run a single test with `pnpm test -t "rejects an empty webClientId"`.

## Testing native changes

There is no way to build the native code from this directory. The TurboModule spec base classes are generated by React Native's codegen at *app* build time, so the Kotlin and Objective-C only compile inside a host app. The example app is that host, and it is what CI builds for both platforms (Android on Linux, iOS on macOS):

```sh
pnpm install              # from the repo root first: this builds lib/, which the example runs
cd example
cp .env.example .env      # add your own Google OAuth client IDs
pnpm install
pnpm prebuild
pnpm android              # or: pnpm ios
```

`example/` has its own `pnpm-workspace.yaml`, which is why `pnpm install` there installs the example and not the library.

You need your own OAuth clients — see [example/README.md](example/README.md). There are no shared test credentials. CI can only prove the native code compiles: a runner can't complete a Google consent screen, so sign-in itself is verified by hand.

In a development build the library prints every error with its cause and fix. Keep `adb logcat -s ReactNativeJS:V GoogleCredentialMgr:V` open on Android (or the Metro terminal on iOS) while you work.

The example runs the **built** package, not the source, so it checks what actually ships. After changing anything in `src/`, run `pnpm example:sync` from the repo root (it rebuilds `lib/` and reinstalls the example's copy), then reload; otherwise the example keeps running the old build. Native changes need a rebuild of the app. After changing anything in [plugin/](plugin/), re-run `pnpm prebuild`, since the plugin only runs at prebuild time.

## The parts that need care

**The user payload is assembled in three places** and they must stay in sync. To add or rename a field on `User`, edit all of:

- the `User` interface and `parseUser` validation — [src/index.tsx](src/index.tsx)
- the `JSONObject` built in `buildUserPayload` — [the Android module](android/src/main/java/com/googlecredentialmanagerlogin/GoogleCredentialManagerLoginModule.kt)
- `resolveUser:` — [the iOS module](ios/GoogleCredentialManagerLogin.mm)

**`id` is the OIDC `sub` on both platforms.** Other code depends on this and it is easy to break: on Android the credential's `.id` field is the *email*, so the module decodes the ID token JWT to read `sub`. Don't "simplify" that away.

**Error codes are a documented contract**, published in three places. Adding one means editing all of them in the same commit:

- `ERROR_REMEDIES` in [src/errors.ts](src/errors.ts) — the source of truth, and where the cause/fix text lives
- a `### CODE` heading in [AGENTS.md](AGENTS.md)
- the table in [README.md](README.md#error-codes)

A test enforces this, so a missing entry fails CI rather than shipping as a doc that reads fine and is wrong. Write the remedy as something the reader can act on without opening anything else — it is appended to the thrown error's `message`, so it is often the only documentation a caller ever sees.

**Device verification.** Three Android APIs and the whole iOS path are unproven on hardware. If you have a device, [docs/manual-verification.md](docs/manual-verification.md) is the protocol — it asks for observed values rather than verdicts, because a promise that resolves proves the bridge returned, not that Google did anything.

## Pull requests

- Keep them focused on one change.
- Make sure lint, typecheck and tests pass.
- Say which platform(s) you actually ran the change on, and on what device or emulator. "Untested on iOS" is a fine thing to write — guessing isn't.
- For API or behaviour changes, open an issue first.
- Add a [CHANGELOG.md](CHANGELOG.md) entry under "Unreleased".

## Releasing

For maintainers:

1. Update the `version` in `package.json`. It drives the podspec version too.
2. In `CHANGELOG.md`, rename the "Unreleased" heading to the new version and date, then add a fresh empty "Unreleased" heading above it.
3. `pnpm publish` — `prepublishOnly` runs lint, typecheck, tests and the build, so the tarball always contains a fresh `lib/`. Check what it will contain first with `pnpm pack --dry-run`.
4. Tag the release: `git tag v<version> && git push --tags`.
